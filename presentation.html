Requirement Analysis · Slide 2 of 7

Functional & Non-Functional Requirements

⚙️ Functional Requirements

Authentication & Registration

  • Player self-registration using campus-issued email only (.edu / .ac.lk / .edu.lk)
  • Admin assigns default password; credentials managed by admin
  • JWT-based secure login with per-role routing
  • Pending players blocked from login until coach approval

Player Enrolment Workflow

  • Players cannot join directly; must pass through coach approval
  • Captain submits player request → Coach reviews → Approve / Reject
  • Coach can directly add players and assign them to a captain
  • Sport category & position captured at registration

Reporting & Evaluation

  • Captain submits daily player reports (Attendance, Discipline, Training Hours)
  • Coach reviews, overrides, and gives feedback on player reports
  • Coach evaluates captain leadership via structured captain reports
  • Director views global metrics; Manager monitors coach performance

🔒 Non-Functional Requirements

Security

  • Passwords hashed using bcryptjs (salt rounds: 10)
  • JWT tokens for stateless authentication; role verified on every request
  • Campus email domain validation at both frontend and backend layers
  • Full audit log trail for all critical user actions

Usability & Performance

  • Single-page application; navigation without full page reloads
  • Role-specific sidebar menus with contextual navigation
  • Responsive glass-morphism UI for desktop and tablet
  • MySQL connection pooling for concurrent query handling

Data Integrity

  • Unique constraints: no duplicate emails, one report per player per date
  • Foreign key cascades to prevent orphaned records
  • Transaction-wrapped registration to ensure atomicity across two tables

Middleware & Security Layer

🔐 JWT Protect Middleware

Every protected route passes through the protect middleware which decodes the JWT and attaches req.user (user_id, role). The directorOnly guard additionally restricts sport management endpoints.

🌐 CORS & Static Files

Express CORS allows the Vite dev server (localhost:5173) to reach the API at localhost:5000. Profile photos served from /uploads as static assets via multer.

📝 Audit Logger Utility

A shared logAction(user_id, action, details) utility writes every significant operation (CREATE_SPORT, APPROVE_PLAYER, SUBMIT_REPORT, etc.) into the audit_logs table.

⚡ Connection Pool

mysql2 promise pool with a limit of 10 concurrent connections, queue-based overflow handling. Registration uses explicit transaction BEGIN / COMMIT / ROLLBACK to ensure user + player rows are inserted atomically.

Core Workflows & Data Flow

Player Enrolment Workflow

1. Registration (3 Paths)
Self-register / Captain submits request / Coach direct-add — all require campus email domain validation at frontend + backend
2. Pending State
Player row inserted with approval_status = 'Pending'. Login attempt returns 403 with informative message.
3. Coach Review
Coach views pending list (with full details: email, sport, position) and selects a captain to assign upon approval
4. Approved & Active
Status set to 'Approved', player linked to captain. Player can now log in and appears in squad rosters & teammates lists
